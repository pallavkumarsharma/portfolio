Building an Integration Centre of Excellence

Establishing the architecture standards, governance frameworks, and engineering culture that became the operational backbone for 50+ enterprise integration projects across healthcare, fintech, and SaaS.

Context

When I joined MinloPro Partners as Associate Manager, the consulting practice had strong individual contributors but no standardised way of doing integration work. Each engagement reinvented the wheel — different naming conventions, different error handling patterns, different approaches to CI/CD. The result was high variability in quality and longer ramp-up times on new projects.

The mandate was clear: build an Integration Centre of Excellence that would raise the floor for every engagement, accelerate delivery, and create an engineering culture the team would actually want to work within.

Approach

I started by auditing three live engagements to identify recurring patterns and recurring problems. The goal wasn't to impose a framework top-down — it was to codify what was already working well and eliminate what wasn't.

From that audit, I identified four foundational pillars for the CoE:

  • Architecture standards — documented API-led connectivity patterns, naming conventions, error handling frameworks, and security policies that every project inherits by default
  • Reusable asset library — a curated set of MuleSoft templates, common connectors, and utility flows that eliminate boilerplate on every new engagement
  • CI/CD pipeline templates — GitHub Actions and Azure DevOps pipeline definitions that new projects clone and customise, rather than build from scratch
  • Security baseline — a standard set of API gateway policies, OAuth 2.0 configurations, and audit logging patterns that every project applies from day one

Outcomes

The reusable asset library alone cut the setup time for new MuleSoft projects significantly. Engineers stopped asking "how do we handle this?" for common patterns and started asking better questions — about business logic, about edge cases, about architecture trade-offs that actually mattered for each specific client.

The CI/CD templates reduced the variance in deployment quality across the team. Environments that previously required manual steps to configure are now reproducible from a pipeline definition.

The most important outcome wasn't a technical one — it was that the team developed a shared vocabulary for architecture decisions. That vocabulary made code reviews faster, onboarding smoother, and client conversations more precise.

Building the team

Managing and mentoring a team of 6 integration engineers across concurrent projects required clarity about expectations at every level. I established a practice of structured architecture reviews for every new engagement — not as a gate, but as a learning mechanism. Every review produced a written decision record that became part of the team's institutional knowledge.

Two engineers on the team have since grown into senior roles. That progression is the outcome I'm most proud of.
